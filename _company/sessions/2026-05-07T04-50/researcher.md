## 🚨 시스템 결함 인식 보고서 (ASV Report)
AI/테크 분야 일반 초보자가 가장 놓치기 쉬우며, 경각심을 느껴야 할 '시스템적 결함(Awareness of System Vulnerability)' 주제 3가지를 선정하고, 각 항목별 손실 근거와 핵심 논점을 정리했습니다. 이 자료는 콘텐츠의 권위(Authority) 확보에 즉시 활용할 수 있습니다.

### ⚠️ [ASV Topic 1] 프롬프트 엔지니어링 신화: '맥락 구조 설계' 부재로 인한 비효율성
**핵심 결함:** 초보자는 복잡한 문제 해결을 오직 **프롬프트(Prompt)**의 기술적 완성도만으로 해결 가능하다고 믿습니다. 이는 마치 엔진이 고장 났는데, 단순히 연료를 잘 넣는 것만으로 수리할 수 있다고 생각하는 것과 같습니다.
**진실 (System Truth):** AI 모델은 강력한 도구일 뿐이며, 실제 시스템 구축에는 **데이터 플로우(Data Flow)**와 **명확한 구조적 설계 원칙(Structural Design Principles)**이 선행되어야 합니다. 프롬프트는 '지시서'이지, '시스템 아키텍처' 자체가 아닙니다.

| 구분 | 내용 | 손실 근거 및 데이터 키워드 (권위 확보용) |
| :--- | :--- | :--- |
| **초보자 오해** | "좋은 프롬프트만 쓰면 어떤 복잡한 비즈니스 문제도 AI가 해결해 줄 것이다." | 프롬프트는 단일 질의에 최적화되어 있으며, 다단계(Multi-step) 검증이나 외부 데이터 연동이 어렵다는 한계 존재. |
| **실제 손실** | *시간 및 자원의 낭비.* 구조 설계 과정 없이 AI 결과물을 그대로 업무에 적용하여 재검토/수정하는 데 드는 비용과 시간적 손실이 가장 큼. | **Key Metric:** 'AI Output Refinement Cycle Time' (재작업 순환 주기). **Evidence:** RAG(Retrieval Augmented Generation) 시스템을 구축하지 않고 단순 프롬프트에 문서를 통째로 넣을 경우, 모델의 환각(Hallucination) 위험이 증가함. |
| **강화 논점** | AI에게 문제를 *요청*하는 것이 아니라, AI가 작동할 수 있는 *환경*과 *규칙* 자체를 설계해야 한다 (System Design Thinking). |

### ⚠️ [ASV Topic 2] LLM의 오해: '챗봇'을 넘어선 자율 에이전트(Agent) 시스템 구축 리스크
**핵심 결함:** 초보자는 LLM을 대화형 인터페이스(Chatbot)로만 인식합니다. 하지만 현대 AI는 단순히 답변하는 것을 넘어, 외부 API 호출, 자체 판단, 반복적 실행 등 **자율적인 행위 주체(Autonomous Agent)**가 되어야 할 필요성이 커지고 있습니다.
**진실 (System Truth):** 단순한 챗봇은 '대화'에만 국한되지만, 진정한 시스템은 '행동(Action)'을 합니다. 에이전트 구조는 모델의 판단력(Reasoning)과 외부 도구 사용 능력(Tool Calling/API Integration)을 분리하여 관리해야 하며, 이 과정에서 발생하는 **상태 관리(State Management)**가 가장 어려운 기술적 병목 구간입니다.

| 구분 | 내용 | 손실 근거 및 데이터 키워드 (권위 확보용) |
| :--- | :--- | :--- |
| **초보자 오해** | "ChatGPT 같은 곳에 지시만 내리면 알아서 복잡한 업무 흐름(예: 예약, 재고 확인 후 발송)을 처리해 줄 것이다." | LLM의 답변은 '가장 그럴듯한 추론'일 뿐이며, 외부 세계와의 상호작용(실제 DB 접근 등)에는 명시적인 코드/워크플로우 설계가 필수. |
| **실제 손실** | *운영상의 오류 및 비용 발생.* 에이전트가 잘못된 API를 호출하거나, 이전 단계의 상태 정보를 잊어버려 (Memory Leak), 업무 프로세스가 중간에 끊기거나 오작동하는 경우. | **Key Metric:** 'Workflow Failure Rate' (워크플로우 실패율). **Evidence:** Agentic AI는 LLM 자체의 성능보다 **Orchestration Layer** (LangChain, CrewAI 등) 설계가 성공을 좌우하며, 이 레이어 설계에 대한 이해 부족이 치명적인 위험 요소임. |
| **강화 논점** | 단순한 질답(Q&A) 시스템 구축을 넘어, '결정-행동-피드백'의 순환 구조를 갖는 최소기능제품(MVP)부터 설계해야 한다. |

### ⚠️ [ASV Topic 3] 데이터 주입 및 보안 오해: 민감 정보 유출 경로 관리 부재
**핵심 결함:** 초보자는 AI 모델에 데이터를 넣는 행위가 '통제된 공간'에서만 이루어진다고 착각합니다. 특히, 비공개적인 회사 내부 문서나 개인의 민감 정보를 프롬프트나 단순 업로드 기능으로 처리할 때 보안적 리스크를 간과합니다.
**진실 (System Truth):** 모든 입력 데이터는 모델 학습 과정에 이용되거나(옵트아웃 불가 시), 또는 중간 서버를 거치면서 로그로 남을 수 있습니다. 민감 정보를 다루기 위해서는 **데이터 가명화/익명화 처리(Anonymization)** 및 **접근 통제 프로토콜**이 필수적입니다.

| 구분 | 내용 | 손실 근거 및 데이터 키워드 (권위 확보용) |
| :--- | :--- | :--- |
| **초보자 오해** | "AI 서비스에 넣는 정보는 회사 기밀로 안전하게 보호된다." | 대부분의 상용 API 사용 약관을 읽지 않거나, '안전하다'는 막연한 신뢰를 바탕으로 중요 데이터를 다루게 됨. |
| **실제 손실** | *법적 리스크 및 금전적 피해.* 경쟁사 기밀, 개인 식별 정보(PII) 등이 유출되어 소송이나 기업 신뢰도 하락을 초래함. 가장 막대한 비용은 '데이터 유출 사고 수습'에 들어감. | **Key Metric:** 'Data Breach Cost Estimate'. **Evidence:** GDPR (General Data Protection Regulation) 등의 법규는 민감 정보 처리 과정의 투명성(Audit Trail)과 통제 가능성을 요구하며, 단순 프롬프트 입력만으로는 이 기준을 충족할 수 없음. |
| **강화 논점** | AI 활용 전 반드시 데이터를 '시스템적으로 분류'하고, 어떤 종류의 데이터가 모델에 들어갈지, 그리고 그 결과물이 어디로 나갈지(Output Destination)를 명확히 정의해야 한다. |
