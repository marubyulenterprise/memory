### 🔍 레퍼런스 1: 모듈형 컴포넌트 기반 (Google Cloud Platform & AWS)
**[핵심 구조]** 서비스 간의 상호작용과 의존성(Dependency)을 보여주는 데 최적화된 형태입니다.
**[분석 목적]** 시스템의 '구조'와 '확장성'에 대한 신뢰도를 높이는 것이 목표입니다.

| 분석 항목 | 상세 내용 | 적용 가이드 (Designer 전달 사항) |
| :--- | :--- | :--- |
| **주요 형태** | 모듈식 컴포넌트(Module Component). 각 서비스가 독립적인 경계(Boundary Box) 안에 갇혀있고, 연결선은 해당 경계를 넘어 흐르는 데이터의 *유형*을 강조합니다. | 노드(Node)를 단순 사각형이 아닌, **독립된 기능 단위로 인식되는 '박스'** 형태로 재정의해야 합니다. 각 박스의 가장자리를 미묘하게 톤온톤 그라데이션 처리하여 물리적 경계를 부여하세요. |
| **색상 팔레트** | 주 색상(Primary Blue)을 전체 배경에 사용하되, 연결선과 데이터 흐름만 강조하는 보조 색상(Accent Color)을 사용합니다. (예: Deep Navy $\rightarrow$ 연한 하늘색 계열의 미묘한 그라데이션). | **톤 분리 원칙:** 컴포넌트 자체는 중립적인 배경색으로 유지하고, '흐르는 데이터'와 '주요 원리'에만 Cyan Blue/Electric Blue를 집중적으로 사용해야 합니다. |
| **가장 큰 장점** | 복잡도가 높아져도 시각적 혼란이 적고, 어떤 컴포넌트가 주된 핵심 엔진인지 명확하게 분리할 수 있습니다. | 연결선(Connection Line)을 단순 화살표로 그리지 말고, **'데이터 패킷 플로우'처럼 보이는 입체적인 띠** 형태로 구현하여 역동성과 중요도를 동시에 부여해야 합니다. |

### 🔍 레퍼런스 2: 워크플로우 순차성 강조 (SaaS Onboarding Flow / Figma)
**[핵심 구조]** 사용자가 거쳐야 하는 단계(Step-by-step)의 논리적 흐름을 보여주는 데 최적화된 형태입니다.
**[분석 목적]** 독자에게 '진행해야 할 순서'와 '다음 액션'에 대한 명확한 안내를 제공합니다.

| 분석 항목 | 상세 내용 | 적용 가이드 (Designer 전달 사항) |
| :--- | :--- | :--- |
| **주요 형태** | 스텝퍼(Stepper) 패턴 또는 수평적 타임라인(Timeline). 시작점과 끝점을 명확히 하고, 각 단계 사이에 '다음으로'라는 방향성이 강하게 느껴집니다. | 현재의 `System Flow Diagram`를 단순 원인 $\rightarrow$ 결과가 아닌, **'단계별 학습 및 개선 과정 (Stage-Gate)'** 구조로 수정해야 합니다. 노드 간 이동에 명확한 숫자가 붙은 진행 바(Progress Bar) 개념을 도입하세요. |
| **색상 팔레트** | 시작 단계는 덜 채워진 색상(Gray/옅은 블루), 현재 강조되는 단계는 가장 진하고 밝은 브랜드 컬러, 완료된 단계는 성공적인 녹색 계열을 사용하여 시각적 성취감을 유도합니다. | `Misconception Alert`를 **'시작점 (Start Point)'**으로 간주하고, 다음 시스템 흐름의 시작 전에 이 '경고'가 반드시 겪어야 할 첫 번째 관문처럼 보이게 해야 합니다. |
| **가장 큰 장점** | 독자가 과정 자체에 몰입하게 만들어 학습 의지를 높입니다. 권위적인 설명이 아니라, '나도 해낼 수 있다'는 실질적 동기 부여를 제공합니다. | 연결선(Connection Line)을 통해 단순히 다음 노드로 가는 것이 아니라, **"이전 단계에서 얻은 A 자산 $\rightarrow$ 다음 단계의 B 프로세스에 활용된다"**라는 구체적인 데이터 이동 맥락을 캡션과 함께 명시해야 합니다. |

### 🔍 레퍼런스 3: 다차원적 관점 분석 (학술 논문 시각화 / BI 대시보드)
**[핵심 구조]** 여러 변수, 역할(Role), 시간 축이 복합적으로 얽혀있는 '복잡계'를 설명하는 데 최적화된 형태입니다.
**[분석 목적]** 콘텐츠에 학술적인 깊이와 다각도 분석의 권위를 부여합니다.

| 분석 항목 | 상세 내용 | 적용 가이드 (Designer 전달 사항) |
| :--- | :--- | :--- |
| **주요 형태** | 스윔레인(Swimlane) 또는 매트릭스(Matrix) 구조. 여러 주체(Actor/Role)가 시간의 흐름에 따라 어떤 책임과 상호작용을 하는지 수평-수직으로 분할하여 보여줍니다. | `System Flow Diagram`를 단순한 단일 플로우로 끝내지 말고, **'누가 이 과정을 거치고', '어떤 데이터 주체(Data Owner)의 관점에서 봐야 하는지'**라는 레이어를 추가해야 합니다. (예: 개발자 시점 vs 기획자 시점). |
| **색상 팔레트** | 참여하는 역할/주체(Actor)마다 고유한 색상을 할당하고, 이 색상이 다이어그램 전체를 통일적으로 관통하도록 적용합니다. 배경은 매우 절제된 무채색을 사용해야 합니다. | Marubyul의 '시스템 아키텍처 원리' 자체가 하나의 주체(Role)가 되어야 하며, 다른 도구들(ChatGPT, Zapier 등)은 그 주체를 보조하는 **'도구적 역할'**로만 색상 구분을 명확히 해야 합니다. |
| **가장 큰 장점** | '나열된 기능의 집합체'가 아니라, '논리적으로 결속된 유기체'라는 인상을 주어 전문적인 권위가 극대화됩니다. | 연결선(Connection Line)에 단순히 화살표를 넣는 것이 아니라, **"이 데이터는 이 역할에서 발생하여 다음 역할로 이동한다"**라는 캡션을 붙여 '흐름의 스토리텔링'을 강화해야 합니다. |

### ✅ Designer 전달 요약 및 Action Items (V2.0 업데이트 지시)

1.  **[필수 개선] 연결선(Connection Line):** 단순히 화살표가 아닌, **데이터 패킷 플로우(Data Packet Flow)** 형태로 리디자인하여 유체적이고 입체적인 느낌을 부여할 것.

3.  **[색상 통일] 주체(Role) 중심 색상 분리:** 다이어그램 내 모든 요소를 '시스템 원리'를 중심으로 재편하고, 다른 도구들은 보조적 역할임을 명확히 하는 **톤온톤의 구조화된 컬러 팔레트 시스템**을 적용할 것.
