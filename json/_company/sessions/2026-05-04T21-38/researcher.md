### 💡 개요: 권위 확보의 논점
대부분의 AI 교육 콘텐츠는 '어떤 툴을 어떻게 사용하는가' (Tool Usage)에 집중되어 있습니다. 하지만 성공적인 자동화 시스템은 도구를 연결하는 *방법론적 원리*와 *예외 처리 설계 능력*에서 나옵니다. 아래 정의된 5가지 오류는 이 근본적인 **시스템 설계 관점의 결함**을 다룹니다.

### 🚩 1. 데이터 변환 및 구조화 실패 (The Data Schema Gap)
AI가 이해하는 데이터를 단순히 텍스트로 취급하고, 원천 데이터에 내재된 비정형성(Non-structured data)이나 누락되는 필드 값을 고려하지 못하는 오류입니다. '데이터는 입력하면 된다'는 착각이 가장 큰 문제입니다.

**🔎 진단 질문 (Diagnostic Questions):**
1.  원천 데이터를 가져올 때, 필수 항목 중 **값이 비어있거나(Null)** 예상치 못한 문자열(Garbage Data)일 경우, 시스템이 멈추지 않고 자체적으로 표준화된 대체값으로 처리하는 로직을 설계했습니까? (데이터 클렌징/검증 단계 여부)
2.  여러 소스에서 모인 데이터를 하나의 체계적인 **스키마(Schema)**로 통합할 때, 각 데이터 필드의 단위(Unit: %, 원, 개수 등)와 포맷 형식을 통일하는 전처리 과정을 거쳤습니까? (데이터 일관성 질문)
3.  만약 핵심 키워드가 텍스트가 아닌 이미지나 음성으로 들어올 경우, 이를 AI가 처리할 수 있는 **표준화된 디지털 데이터 형태**로 변환(OCR, STT 등)하는 모듈을 구축하고 테스트했습니까? (다중 모달리티 입력 대응 질문)

### 🚩 2. 단일 실패 지점 의존성 (Single Point of Failure, SPOF)
시스템의 핵심 기능이나 외부 API 호출이 하나의 경로에만 의존할 때 발생합니다. 해당 요소가 다운되거나 속도가 느려지면 전체 자동화 파이프라인이 무력화되는 치명적인 구조적 결함입니다.

**🔎 진단 질문 (Diagnostic Questions):**
1.  메인 프로세스가 외부 서비스 A(예: 특정 API)에 의존할 때, 해당 서비스가 **응답 지연 또는 오류를 반환**하면 시스템이 재시도(Retry Logic)하는 로직과 최대 실패 횟수를 설정했습니까? (복원력 질문)
2.  파이프라인의 중간 단계 중 하나가 마비될 경우, 전체 프로세스를 강제로 중단시키는 것이 아니라 **최소한의 기능만 유지**하여 알림을 보내거나 수동 개입 지점으로 이관하는 '우회 경로'를 설계했습니까? (Fallback Mechanism 질문)
3.  핵심 데이터를 저장하는 데이터베이스나 클라우드 스토리지 자체가 장애가 발생했을 경우, 백업 시스템으로 **자동 전환(Failover)**할 준비와 테스트를 완료했습니까? (인프라 안정성 질문)

### 🚩 3. 비선형적 피드백 루프 부재 (The Feedback Loop Void)
단순히 A $\to$ B $\to$ C 순서로 데이터를 흘려보내는 '직선형' 자동화에 머무는 오류입니다. 실제 시스템은 결과물을 보고 다음 행동을 *조정*해야 하는 비선형적 피드백 루프가 필수적인데, 이를 간과합니다.

**🔎 진단 질문 (Diagnostic Questions):**
1.  AI가 생성한 1차 결과물(A)을 사람이 검토하고 수정할 때, 그 **수정 내용이 다음 단계(B)의 입력 데이터로 자동으로 피드백되어 반영**되도록 시스템 로직을 구축했습니까? (인간 개입 기반 학습 질문)
2.  자동화 프로세스의 중간 지점에서 발생한 '이상 징후'나 '예외 값'에 대해, 단순히 로그만 남기는 것이 아니라 **담당자에게 즉각적인 경고 알림(Alert)**을 보내는 시스템이 갖춰져 있습니까? (모니터링/경보 질문)
3.  최종 결과물이 비즈니스 목표(KPI)를 달성하지 못했을 때, 그 원인을 분석하여 **'다음 주 프로세스 개선점'으로 자동으로 리포팅**하고 다음 사이클에 반영하는 순환 구조가 있습니까? (지속적 최적화 질문)

### 🚩 4. 사용자의 '의도(Intent)' 기반 설계 부족
사용자가 *무엇을 할 것인지*에 초점을 맞추어 도구를 사용하는 것이 아니라, *시스템이 무엇을 할 수 있는지*에만 초점을 맞춰 시스템을 구축하는 오류입니다. 결과적으로 비즈니스 목표와 무관한, 기능적인 데모 수준의 자동화가 됩니다.

**🔎 진단 질문 (Diagnostic Questions):**
1.  자동화 파이프라인 시작 전, **'최종 달성해야 할 핵심 성과 지표(KPI)'를 명확히 정의하고**, 이 목표와 관련 없는 모든 기능을 제외했습니까? (목적 중심 설계 질문)
2.  사용자의 '질문 의도'가 모호할 때(Ambiguity), 시스템이 추측에 의존하는 대신 **"어떤 목적으로 사용하시겠어요?"** 와 같은 구체적인 컨텍스트를 요청하여 정확한 방향을 잡도록 유도합니까? (컨텍스트 파악 질문)
3.  자동화의 목표가 '시간 절약'인지, 아니면 **'새로운 비즈니스 기회 발굴'**인지 등, 궁극적으로 해결하려는 문제의 근본적인 성격(Pain Point)을 정의하고 설계에 반영했습니까? (문제 인식 깊이 질문)

### 🚩 5. 비용 및 확장성 모델링 부재 (The Cost & Scale Blind Spot)
초기 구축 단계에서는 저렴해 보이지만, 사용량이 증가하거나 시스템이 복잡해지면서 API 호출 비용, 데이터 처리 시간(Latency), 유지보수 난이도가 기하급수적으로 증가하는 것을 간과하는 오류입니다.

**🔎 진단 질문 (Diagnostic Questions):**
1.  현재의 트래픽 수준으로만 비용을 계산하고 있습니까? 아니면 **'향후 3년 내 사용자 규모가 5배 증가했을 때'의 예상 API 호출량 및 비용 모델링**을 완료했습니까? (미래 예측 기반 질문)
2.  시스템의 핵심 로직 중, 처리량이 늘어날수록 병목 현상을 일으키는 특정 모듈(예: 이미지 생성/대용량 데이터 분석)이 있다면, **더 저렴하거나 빠른 대체 기술 스택**으로 교체할 계획을 마련했습니까? (최적화 및 비용 효율 질문)
3.  자동화 시스템의 유지보수 측면에서, 코드를 이해하고 수정할 수 있는 내부 인력의 역량(기술 부채)을 고려하여 **너무 복잡한 단일 구조**를 만들지 않았는지 점검했습니까? (운영 용이성 및 지속 가능성 질문)
